# PDF parity fixtures (issue #258)

- `guide.pdf` is generated by `make_fixture.py` (standard library only, no
  embedded font). It has four pages: page 1 and page 3 contain text, page 2 is
  blank, and page 4 contains only spaces. Text covers Latin-1 accents, an en
  dash, PDF-escaped delimiters, an indented line, a paragraph gap, and a run of
  literal spaces that pdfplumber collapses to one.
- `blank.pdf` is generated by the same script. No page has non-whitespace text.
- `broken.pdf` has a page content stream with an unterminated string literal.
  It pins the strict page-content preflight: the lenient parser would silently
  ingest a partial page.
- `encrypted_empty.pdf` has an empty user password and an owner password;
  `encrypted_secret.pdf` requires the user password `secret`. They pin the
  empty-password decrypt path and the non-empty-password rejection.
- `corpus/` contains eight differential cases (two-column, table, two fonts,
  long page, paragraph gaps, WinAnsi unicode, delimiters, multi-page with a
  blank middle) and a pdfplumber oracle (`corpus/goldens.json`). Every case must
  render byte-for-byte identically; rotated/multi-column layout beyond this set
  remains a documented limitation.
- `goldens.json` is generated by `generate_goldens.py` from the **real** Python
  path: it calls `process_pdf_file` and `_retain_document` (with
  pdfplumber-dependent rendering and the real synthesis metadata) and records
  the pdfplumber per-page text, rendered content, retain calls (ids, chunks,
  metadata, tags, timestamp), timestamp-formatting and mtime cases, and source
  hashes.

Regenerate the PDFs (no dependencies):

```bash
python3 rust/crates/engram-ingest/fixtures/pdf/make_fixture.py
```

Regenerate the oracle with the deployed flow interpreter (Python 3.14,
pdfplumber, sklearn/networkx):

```bash
PYTHONPATH=src ~/.engram/venv/bin/python \
    rust/crates/engram-ingest/fixtures/pdf/generate_goldens.py
```

Regenerate the differential corpus and its oracle:

```bash
python3 rust/crates/engram-ingest/fixtures/pdf/corpus_make.py
PYTHONPATH=src ~/.engram/venv/bin/python \
    rust/crates/engram-ingest/fixtures/pdf/corpus_goldens.py
```

`tests/pdf_parity.rs` checks the fixture SHA-256 against the goldens, then
compares rendered content and planner output byte-for-byte. Review any
`goldens.json` diff together with the Python source or fixture change; CI does
not regenerate it because the oracle needs the flow venv.

## Scope and known limits

Parity is pinned to these fixtures, which exercise the contract in
`src/engram/flows/configured.py:271-296`: page markers, one blank page, a
whitespace-only page, non-ASCII text, line trimming, space-run collapse, and
paragraph-gap collapse. Both implementations extract only embedded text;
scanned/image-only PDFs yield no retain calls and OCR remains out of scope.

Layout-heavy PDFs (multi-column, tables, rotated text) may still group lines
differently between pdfplumber and the pure-Rust `pdf-extract` crate. The Rust
rendering normalizes line edges, collapses whitespace runs, and removes empty
lines to match pdfplumber's `extract_text` shape, but it does not reproduce
pdfplumber's full layout algorithm.

The Rust preflight rejects corrupt page and Form XObject content (strict lopdf
content decode), requires xref objects and stream lengths to resolve, and caps
FlateDecode expansion at 64 MiB per stream / 256 MiB per document before
extraction. Only unencoded and single-`FlateDecode` streams are accepted; other
filter chains are rejected explicitly instead of being inflated without a
bound. DCT/JPX image streams are exempt from expansion caps. Pagetree-inherited
`/Resources` are resolved before Form XObjects are validated, and NUL/form-feed
content whitespace is rejected because the extractor stops at those bytes.
