# #258 PDF extraction parity — production-readiness evidence

Date: 2026-11-27
Branch: `feat/258-pdf-parity` (base `origin/main` at #257)
Scope: native Rust PDF ingestion for `document_format = "pdf"` docs sources.

## Control basis

Authoritative control excerpts were retrieved from the NIST SP 800-53 Rev.5
OSCAL catalog (`usnistgov/oscal-content`) and the OWASP ASVS 5.0.0 English
chapters on 2026-11-27, retained in Engram under tags
`project:engram, audit, fedramp, nist-800-53-rev5, asvs-5.0, authoritative-reference`,
and recalled for this audit. FedRAMP Rev.5 baselines adopt the NIST controls
cited here. The wider production-readiness matrix (including N/A areas) is the
companion audit report for PR #260.

## Preserved Python contract

`src/engram/flows/configured.py:271-296` (`process_pdf_file`):

- pages are numbered 1-based in source order; blank pages are omitted without
  renumbering later pages;
- each participating page renders as `--- Page {n} ---\n\n{text}` and pages
  join with `\n\n`;
- a whitespace-only render returns before `_retain_document`;
- ids, Markdown chunking, synthesis metadata, tags, and the file timestamp use
  the same `_retain_document` path as Markdown.

## Implementation

- `config.rs`: `document_format` is parsed into `DocumentFormat`
  (`markdown`/`pdf`, with the Python `md`/case aliases) on `DocsSource`; the
  startup rejection is removed; unknown formats still fail validation.
- `pdf.rs`: pure-Rust `pdf-extract` 0.12 (MIT) parses bytes already read by the
  scanner. A preflight loads the document, applies the same empty-password
  decryption as pdf-extract, requires every xref-referenced object and stream
  `/Length` to resolve, strict-decodes page and Form XObject content with
  lopdf's strict parser (the lenient parser silently truncates corrupt
  streams), bounds every stream it may inflate, catches dependency panics,
  normalizes line edges/space runs/blank lines to pdfplumber's `extract_text`
  shape, and renders the Python marker contract. Supported stream encodings are
  unencoded and `FlateDecode`; other filter chains are rejected explicitly
  rather than decompressed without a bound. Input files are capped at 256 MiB
  before reading; pages, per-page content, and Form XObject nesting/count are
  bounded.
- `scan.rs`: chooses Markdown decode or PDF rendering per source; rejects a PDF
  over the input cap before reading; the manifest
  hash is SHA-256 of the rendered content (not PDF bytes), so identical text is
  not a change; `size_bytes` stays the original file size.
- `runtime.rs`: the ledger `sources.document_format` now records the source's
  real format instead of the Markdown default.
- No OCR, no Python/pdfplumber subprocess, no resident service, and no
  CocoIndex removal. Markdown behavior is unchanged.

### SI-10 information input validation; ASVS 1.1.1, 1.4.1–1.4.3, 2.2.1, 5.2.1–5.2.3

- `config::tests::accepts_pdf_format_and_defaults_to_markdown` proves `pdf`
  (including case alias), omitted defaults, and `docs_format = "md"`.
- `config::tests::rejects_unknown_formats` proves unsupported formats still
  fail with the Python-compatible message.
- `scan::tests::malformed_pdf_aborts_the_snapshot`,
  `pdf::tests::corrupt_page_content_is_rejected_instead_of_partially_ingested`,
  `pdf::tests::page_content_references_must_resolve`,
  `pdf::tests::form_xobject_content_is_strictly_validated`,
  `pdf::tests::object_table_rejects_unloaded_xref_entries`,
  `pdf::tests::stream_length_must_be_present_integral_and_matching`,
  `pdf::tests::malformed_pdf_is_an_error_not_a_panic`, and
  `pdf::tests::panic_boundary_reports_panic` prove malformed/untrusted PDF
  structure becomes a source-level error, not a crash or partial snapshot.
  Page and Form XObject content use lopdf's strict parser because the lenient
  parser silently truncates after a corrupt operator; a truncated page would
  otherwise be ingested and delete the chunks it no longer contains. Content
  using NUL/form-feed whitespace is rejected explicitly because the extractor's
  lenient parser would stop there, and `Resources` inherited from a `/Pages`
  node are resolved before Form XObjects are validated.
- `pdf::tests::decompression_bomb_is_rejected_before_extraction`,
  `pdf::tests::stream_and_document_expansion_caps_are_enforced`,
  `pdf::tests::unsupported_filter_chains_are_rejected_and_image_codecs_are_exempt`,
  and `pdf::tests::flate_checksum_damage_falls_back_to_raw_deflate` prove the
  stream caps (64 MiB per stream, 256 MiB per document), the explicit rejection
  of unsupported filter chains, and lopdf-compatible zlib fallback.
- `scan::tests::oversized_pdf_is_rejected_before_reading` proves a PDF above
  the 256 MiB input cap fails before allocation.
- `pdf::tests::page_content_budget_is_enforced` and
  `pdf::tests::deeply_nested_form_xobjects_are_rejected_without_stack_overflow`
  prove per-page content and Form nesting limits fail closed instead of
  exhausting memory or the stack.
- `scan::tests::unreadable_file_aborts_the_snapshot` proves an unreadable PDF
  aborts the snapshot instead of producing a partial deletion view.
- `tests/pdf_corpus_parity.rs::every_corpus_case_matches_pdfplumber_byte_for_byte`
  runs eight differential cases (two-column, table, two fonts, long page,
  paragraph gaps, WinAnsi unicode, delimiters, multi-page with a blank middle)
  and fails on any render divergence from pdfplumber's oracle.
- `runtime_postgres.rs::corrupt_pdf_skips_the_source_and_leaves_the_manifest_untouched`
  first ingests a valid PDF, then swaps in the corrupt fixture and proves the

- `scan::tests::pdf_sources_ignore_markdown_decode_semantics` proves the

## Known limits and residual risk

- Parity is pinned to the committed fixture plus eight differential corpus
  cases, which all match byte-for-byte. Rotated text and layout order beyond
  those cases still may differ from pdfplumber (a rotated-text probe produced
  reversed character-per-line output in pdfplumber); the pure-Rust extractor
  does not reproduce pdfplumber's full layout algorithm. This is documented in
  `fixtures/pdf/README.md` and is the same class of heading-less chunk
  instability already accepted in `docs/COCOINDEX_DEPRECATION.md`.
- Scanned/image-only PDFs produce no text in either implementation; OCR remains
  out of scope.
- FlateDecode streams are inflated with a hard cap during preflight (64 MiB
  per stream / 256 MiB per document), so a classic decompression bomb is
  rejected before extraction. Only unencoded and single-`FlateDecode` streams
  are accepted; other filter chains (including multi-filter arrays) are
  rejected explicitly instead of being inflated without a bound. DCT/JPX image
  codec streams are exempt because the extractor does not inflate them.
- Page/Form content using NUL or form-feed whitespace is rejected explicitly;
  lopdf's extraction parser stops at those bytes, and accepting them in the
  preflight would have allowed silent truncation.
- The preflight parses the document and then `pdf-extract` parses it again, so
  peak work is roughly two parses plus validation inflations. This is an
  accepted CPU/memory cost for the integrity guarantees; dropping the first
  document before extraction keeps it from holding two parsed documents.
- `pdf-extract` treats every XObject as a content stream, including image
  XObjects. A crafted image stream whose bytes happen to look like text
  operators could emit spurious text; the preflight skips image XObjects, but
  replacing the extractor's `Do` handling would require forking it and is out
  of scope. Ordinary image-only PDFs still produce no text.
- `file_timestamp_from_metadata` now has an injected-offset variant; four fixed
  nanosecond mtimes are compared with Python `datetime.fromtimestamp` in CI
  (`file_mtime_conversion_matches_python_fromtimestamp`).
- Password-protected PDFs (non-empty user password) are rejected as an
  extraction error. Empty-user-password encrypted PDFs are decrypted the same
  way pdf-extract/pdfplumber do; both cases are committed fixtures and tested.
- `pdf-extract` panics are caught, but a dependency that aborts the process
  instead of unwinding would still terminate the runtime; the release profile
  keeps `panic = "unwind"` (no `panic = "abort"` override).
- A rejected PDF (corrupt, unsupported, or over the stream cap) skips the whole
  source snapshot for that pass, exactly like an unreadable file. Per-file
  quarantine while applying the rest of the root is a larger ledger policy and
  is explicitly out of scope for #258.
