## 2026-08-06: Hook-Delivered PR Review Checklist — Extending the Correction-Enforcement Hooks to Inject Reviewer Expectations, Not Just Block Contradictions

**Context**: `osac-service-provider`'s `CLAUDE.md` grew a "Pre-PR review
checklist" section distilling recurring reviewer feedback across several
PRs — error mapping (`grpcstatus.Errorf` vs. bare `fmt.Errorf`), response
field consistency across return paths, verify-don't-assume for external
data shapes, comment/decision length, and `DD-*`-vs-exploration placement.
The ask: surface this automatically during implementation planning so it
stops being something a human reviewer has to repeat. Two options were
explicitly ruled out up front:

- **Editing `CLAUDE.md` directly** — this file is read by every
  contributor's Claude Code, most of whom don't use Engram/Hindsight at
  all. Injecting Engram-specific process content there is conflictive with
  a shared, non-Engram project file.
- **Relying on `AGENTS.md`/rule-file content in general** — "it's been
  proven enough times that the model will ignore at will the contents of
  CLAUDE.md and AGENTS.md" (direct user framing). Advisory context that a
  model can choose to skip, or that a context-summarization pass can
  silently drop, isn't a fix for a *recurring* problem.

**Design: reuse the existing hook pair, add a third member sharing its
marker.** The 2026-08-03 Deterministic Correction Enforcement hooks
(`detect-plan-kickoff.sh` + `post-plan-hindsight-check.py`, see below)
already had exactly the right shape: a `beforeSubmitPrompt` detector that
fires once per plan kickoff, handing off to tool-call hooks via a
per-session marker file. Adding `post-plan-checklist-reminder.py`
(`postToolUse`, same matcher, same marker) as a third member was cheaper
and more consistent than inventing a parallel mechanism.

**Spike before implementing**: the one genuinely unverified assumption —
that `postToolUse` fires with the *same* `session_id` as `preToolUse` for
the same tool call (only checked for `preToolUse`↔`beforeSubmitPrompt`
previously) — was spiked with a disposable logging hook pair before
writing any real code. Confirmed: identical `session_id` across
`preToolUse` and `postToolUse` for one `Shell` call. This is what makes the
hand-off safe: the reminder hook can look up the same marker the enforcer
already read.

**Blast radius was the hard part, not the feature itself.**
`post-plan-hindsight-check.py` is one canonical file, symlinked identically
into all 17 previously-onboarded repos (3 kubernaut + 14 dcm-project). The
checklist feature needed the enforcer's marker-deletion timing to change
(defer deletion so the reminder hook can still read it after an allow) —
but only for the one repo that actually has a checklist
(`osac-service-provider`), not for the other 16. Two framings were
considered:

- Gate on a coarse `project == "dcm"` label — rejected: it would make *all*
  14 dcm-project repos' behavior technically different even though 13 of
  them have no checklist to defer for, and it hardcodes a project taxonomy
  into a script that shouldn't need to know it.
- **Gate on file existence** (chosen): the enforcer checks whether
  `~/.hindsight/review-checklists/<repo>.md` exists for the marker's `repo`
  field before deciding whether to defer deletion at all. No file → exactly
  today's unconditional-immediate-unlink behavior, byte-for-byte. This
  makes the behavioral change provably scoped to precisely the repos with a
  checklist file (one, today), not to a label — adding a checklist for
  another repo later is "add a file + commit," no script change, and
  kubernaut can never be affected since it will never have a matching file.

Both the shared enforcer's tests and the new reminder's tests explicitly
cover the "no checklist file for this repo" path (not just the
has-checklist path) specifically to make this claim verifiable, not just
asserted.

**Content storage tradeoff**: a bare file under `~/.hindsight/` has no
tamper-visibility (same trust boundary as the hook scripts themselves — a
same-user local attacker could modify either one identically). Storing the
checklist as a git-tracked file inside *engram's own repo*
(`hooks/review-checklists/osac-service-provider.md`) and symlinking the
whole directory into `~/.hindsight/review-checklists/` (mirroring the
existing pattern for `contradiction_resolution.py`) gives a real integrity
signal — tampering shows up in `git diff`/`git log` — without ever touching
`osac-service-provider`'s own repo. A lightweight `is_safe_checklist_content()`
runtime check (max ~3000 chars, no URLs, no obvious
prompt-injection phrasing like "ignore previous instructions") was kept as
cheap defense-in-depth on top, explicitly scoped as *not* a substitute for
the git-history control — it also catches accidental corruption, not just
malicious edits.

**Gap discovered and closed while scoping this**: `kubernaut-v1.5` and
`kubernaut-v1.6` (two additional local kubernaut worktree clones) turned
out to have *no* `.cursor/hooks.json` at all — the original
`kubernaut_dcm`-scoped rollout of the base hook pair on 2026-08-03 missed
them entirely. `hooks/install.sh` was extended with kubernaut-path
auto-detection (any path containing `/kubernaut`) specifically so this
backfill — and any future kubernaut clone — gets exactly the base
detector+enforcer pair, never the checklist reminder, without a separate
code path.

**Outcome**: `hooks/_write_plan_marker.py` gained `detect_repo_name()` and
a `repo` marker field; `post-plan-hindsight-check.py`'s marker-deletion
became conditional on checklist-file existence (with a `deny` outcome
still deleting immediately regardless, since `postToolUse` never fires
after a `preToolUse` deny — confirmed in the original 2026-08-03 spike);
`hooks/install.sh` and `_merge_hooks_json.py` gained a 4th optional CLI arg
and kubernaut auto-detection; all 14 dcm-project repos were re-installed to
pick up the third hook, `kubernaut`/`kubernaut-console`/`kubernaut-operator`
were left untouched entirely, and `kubernaut-v1.5`/`kubernaut-v1.6` were
backfilled with the base pair only. New/updated tests cover repo detection,
the conditional-unlink matrix (no-file / allow-with-file / deny-with-file /
timeout-with-file), the 3-hook merge (including the kubernaut
empty-reminder-arg case), and the reminder hook's sanity-check and
marker-cleanup behavior.

## 2026-08-05: Two Postgres Outages in Two Days — pg0-Embedded's Self-Managed Lifecycle Was the Actual Root Cause, Fixed by Decoupling It

**Context**: `hindsight` and `cocoindex-code` MCP tools both failed with
"connection refused on `localhost:5432`" this morning. This is the *second*
Postgres outage in as many days sharing the same underlying cause class:
`hindsight-api`'s embedded `pg0` Postgres owns its own start/stop lifecycle,
and two independent things can take that lifecycle down without touching
Postgres's actual data at all.

**Incident 1 (2026-08-04)**: a stale PID bug. `pg0`'s liveness check reads
the PID out of `<data_dir>/postmaster.pid` and only verifies *some* process
holds that PID number — not that it's actually `postgres` (no
`/proc/<pid>/comm`/cmdline check). After a reboot, a recycled low PID got
reassigned to an unrelated process (`TextInputMenuAgent`), so
`ensure_running()` false-positived and skipped starting Postgres entirely,
producing a silent crash loop. Fixed that day by invalidating the stale PID
in `instance.json` and re-running `pg0 start`. This is an upstream bug in the
`pg0-embedded` package itself, not something patchable in Engram code.

**Incident 2 (2026-08-05, ~01:00)**: a different mechanism, same symptom.
The nightly `hindsight-blue-green-restart.sh` job (see
[FINDINGS.md](../FINDINGS.md) 2026-08-02 for why it exists) failed its
`launchctl bootstrap` call with "Bootstrap failed: 5: Input/output error" —
consistent with `gui/<uid>` bootstrap requiring an active Aqua (GUI login)
session, which wasn't available at 1 AM. Around the same time, the embedded
Postgres received a clean `pg_ctl stop -m fast`. `hindsight-api` itself
relaunched via its own `KeepAlive`, but nothing relaunched Postgres — the app
came back up in a degraded state, unable to connect to its database.

**Initial misdiagnosis**: before the actual cause was found, the
investigation first assumed a Podman-managed Postgres (wrong — this project
doesn't use Podman for Postgres) and then a Homebrew `postgresql@16` (also
wrong, and installing it created a *second*, unrelated problem: a real port
conflict with `pg0` on 5432 once `pg0` tried to restart). Both dead ends were
directly corrected by the user before the actual `pg0`-embedded architecture
was identified. Notably, hindsight-docs already had this exact lesson
recorded from a prior incident — *"connection refused on port 5432 doesn't
necessarily indicate the expected Postgres instance died; requires checking
which Postgres is expected first (`DEFAULT_DATABASE_URL`, `pg0`, or
embedded-db config) before consulting system package manager"* — but it
wasn't recalled at the start of this investigation, since recalling it
requires `hindsight` to be up, which was itself the thing that was down. A
documented lesson that depends on the very system it's warning about being
broken has an inherent blind spot; the fix below removes the underlying
fragility instead of relying on remembering the lesson faster next time.

**Fix — decouple Postgres from both failure surfaces.** Both incidents share
one root cause: Postgres's uptime was coupled to `hindsight-api`'s own
process lifecycle and to a restart script's ability to successfully
`launchctl bootstrap`. Neither has anything to do with Postgres itself.
Postgres now runs as its own independently-supervised launchd LaunchAgent
(`launchd/io.vectorize.hindsight.postgres.plist`), using the exact same PG
18.1.0 binary and the same 12GB data directory (`~/.pg0/instances/hindsight/data`,
extensions `vector 0.8.1` + `pg_trgm 1.6` already installed) — no data
migration needed. `hindsight-api` connects to it via a plain
`HINDSIGHT_API_DATABASE_URL=postgresql://hindsight:hindsight@localhost:5432/hindsight`
in `config.env`, which makes `parse_pg0_url()` return `is_pg0=False` and
bypasses `EmbeddedPostgres`/`resolve_database_url()` entirely — confirmed via
`engine/memory_engine.py` and `engine/db/postgresql.py`; note the URL must be
a plain libpq-style string, not `postgresql+asyncpg://`, which crashes
`asyncpg.create_pool()` on the hot path. `COCOINDEX_PG_URL` already pointed
at this same instance/database and needed no change — CocoIndex and
Hindsight were already sharing one physical Postgres, just one that could be
brought down as a side effect of two things unrelated to it.

One deliberate behavior change made at the same time: `fsync` was switched
from `off` (pg0's default, replicated via undocumented `-c` flags baked into
its Rust binary — confirmed via `strings`, not read from any config file) to
`on`, since this is now permanent always-on infrastructure rather than a
disposable embedded instance, and the durability trade-off is no longer
implicit.

**Verified**: cutover took under a minute (stop old instance, bootstrap new
plist, `pg_isready`, confirm `SHOW fsync` is `on`); both `hindsight` recall
and `engram_code_search` MCP tools worked immediately after; killing the new
postmaster's PID directly (`kill -9`) confirmed launchd's `KeepAlive`
relaunches it within ~10s (throttled by `ThrottleInterval: 5`) with zero
script or manual intervention — the exact property neither prior incident
had. As a side effect of restarting both `hindsight-api` colors to pick up
the new `DATABASE_URL`, also discovered and fixed that the "blue" instance
had been silently unloaded from launchd entirely (likely the same
bootstrap-without-Aqua-session failure class, on a previous restart cycle)
and re-bootstrapped it.

**Follow-up not done**: the restart script's `launchctl bootstrap` failure
under a non-Aqua session is still unresolved as a *general* launchd
limitation — it just no longer matters for Postgres specifically, since
nothing ever calls `bootstrap` on its job after the one-time initial
install.

## 2026-08-04 (same day, follow-up): Deterministic Correction Enforcement — Advisory Rules Can't Be the Whole Answer, So We Built a Harness Hook That Can't Be Skipped

**Context**: recurring concern that the same corrections (TDD RED/GREEN/REFACTOR
phases collapsed into one, methodology gaps) keep happening day after day
despite the nightly learning pipeline and cursor rules already documenting
them. Direct question: is this a tooling/harness problem rather than a
memory-content problem? Diagnosis landed on a **compliance-verification
gap**: `recall()` and rule files are advisory — a model can choose not to
call `recall`, and a summarized/compacted context can silently drop a rule's
instructions, so a *documented* convention and an *enforced* one are not the
same thing. Cursor hooks were identified as the one mechanism the model
cannot simply decide to skip, matching the explicit ask: "harness hooks is
not an option for the model to ignore" (unlike `AGENTS.md`/rule files, which
are).

**Design goal**: a hook pair that, on plan-implementation kickoff, checks
the plan's stated approach against `cursor-memory` for a real semantic
contradiction with an established convention, and — only on a genuine
conflict — hard-blocks the first real tool call with an explanation, rather
than a soft/ignorable warning.

**Spike 1 — `CreatePlan` itself is unhookable.** A `postToolUse` hook
matched on `CreatePlan` never fired, with or without an explicit `matcher`.
Ruled out entirely as an attach point.

**Spike 2 — `beforeSubmitPrompt` fires reliably but can't inject context.**
Cursor auto-submits a fixed boilerplate message
("Implement the plan as specified... Don't stop until you have completed
all the to-dos.") immediately after a plan is confirmed through the UI.
`beforeSubmitPrompt` fires reliably on this and matches the same
`session_id` a later `preToolUse` call on the same turn sees — a usable
correlation key. But two things it does *not* give: (1) despite docs
suggesting `attachments` carries the confirmed plan, that field was
consistently empty in every real capture — worked around with a
"newest-`mtime`-under-`~/.cursor/plans/`" heuristic instead; (2) it cannot
inject `additional_context`/`user_message` into the model's turn at all —
confirmed by direct empirical capture, contradicting an initial assumption.

**Spike 3 — `preToolUse` `agent_message` on `deny` is a confirmed Cursor
bug.** First hard-block attempt: `preToolUse` returning
`{"permission": "deny", "agent_message": "..."}`. The tool call was
correctly blocked, but the model only ever saw a generic
"Rejected: Shell blocked by preToolUse hook" — never the custom message.
Cross-checked against Cursor's own docs/community forum, which confirmed
this as a known, staff-acknowledged bug (`agent_message` on `preToolUse`
deny, and `user_message` on `beforeSubmitPrompt`, don't reach the model).
This looked like it killed the hard-block design outright — downgraded to
an advisory `postToolUse` + `additional_context` approach (confirmed
working: reliably reaches the model as a `system_reminder`), at the cost of
never actually *preventing* the first violating action, only flagging it
after the fact.

**Spike 4 — reversal: `preToolUse` `user_message` (not `agent_message`)
*does* reach the model.** Re-tested systematically with a throwaway hook
emitting both fields side by side on the same deny. `agent_message`
confirmed still broken exactly as before; `user_message` — despite the same
docs/forum thread saying otherwise — reliably reached the model's context.
This directly contradicts the published documentation but was reproduced
consistently across repeated calls. Reinstated the hard-block design using
`permission: deny` + `user_message`, dropping `agent_message` entirely.
Also confirmed in the same spike: `postToolUse` never fires at all for a
call `preToolUse` already denied (no double-logging concern).

**Spike 5 — real latency required a subprocess-isolated hard watchdog, not
just a timeout kwarg.** `contradiction_resolution.resolve()` (existing,
already-validated module — `recall()` + Vertex-AI-backed
`check_contradiction()`) measured 5-10s typical with real credentials, but
both `recall()`'s HTTP client and `check_contradiction()`'s `litellm` call
have their own internal retry loops that are uncapped in aggregate — a
`preToolUse` hook blocking indefinitely on a hung network call would be far
worse than no check at all. Fix: the enforcer never calls `resolve()`
in-process; it always spawns a **separate child process**
(`hooks/_hindsight_check_worker.py`) via `subprocess.run(..., timeout=N)`
and treats `TimeoutExpired` as a normal fail-open path. Confirmed
empirically that this cleanly kills a genuinely hung child with no orphaned
process left behind.

**Spike 6 — `hindsight-api`'s `/recall` endpoint silently 400s past 500
tokens, which would have made the check a permanent silent no-op.**
Preflighting the false-positive rate against 12 real historical plan files
using their full plan-body text (up to ~3,000 chars / ~780 tokens) failed
every single `recall()` call with `HTTP 400`Bad Request` —
`spike/hindsight_client.py`'s own error handling swallows that into an
*empty* result list, which `resolve()` then correctly (from its own logic's
perspective) treats as "nothing to compare against, retain" — meaning the
enforcer would have run, cost real latency, and **never once actually
checked anything**, with no error surfaced anywhere. Fix: query
`recall()` with the plan's `overview` frontmatter field only (1-3 sentences
on every plan file inspected) — well under budget, and arguably the
*better* granularity anyway (stated intent, not implementation detail).

**Spike 7 — false-positive preflight surfaced a real design ambiguity, not
just a bug.** Re-ran the 12-plan sample with the corrected `overview`-only
query (read-only replica of `resolve()`'s decision logic, deliberately not
calling the real function to avoid writing to the live pending-contradiction
queue during a test): **1/12 (8.3%) flagged**, confidence 0.92, with a
semantically coherent explanation — the flagged plan introduced a new
structural guard that *intentionally* superseded an existing, more
permissive convention. This is the correct behavior of a contradiction
*detector*, but it exposed that `resolve()` has no way to distinguish "this
plan makes a genuine mistake" from "this plan deliberately, correctly
evolves the convention" — both look identical as a semantic conflict.
Resolved by making the marker's one-shot consumption an explicit design
choice rather than an implementation detail: the marker is deleted
**before** the check runs (crash-safe) and is never reinstated, so a deny is
a one-time speed bump per plan, not a permanent lock — the model sees the
explanation once, and a retry (same or revised action) passes through
cleanly via the "no marker" fast path.

**Spike 8 — `Task` subagents get a different `session_id`, a confirmed
coverage gap.** A throwaway `preToolUse` logging hook captured
`session_id` for a `Shell` call issued directly in the parent conversation
versus the same call issued through a `Task` subagent: completely different
IDs. Since the marker hand-off from `hooks/detect-plan-kickoff.sh` to
`hooks/post-plan-hindsight-check.py` is keyed by `session_id`, any plan
whose implementation is delegated to a subagent gets **zero** enforcement
coverage — not circumvention, just an unmatched lookup. Accepted as an
explicit scope limit for this pass rather than solved (would need a
`conversation_id`-based scheme instead, which trades away some of
`session_id`'s other useful properties).

**Implementation** (`hooks/` in this repo — see `docs/NEW_PROJECT_SETUP.md`
step 12 for the install procedure): `detect-plan-kickoff.sh`
(`beforeSubmitPrompt`) matches the boilerplate, extracts the newest plan
file's `overview`, detects the target project (`kubernaut`/`dcm`) from
`workspace_roots` by path prefix, writes a per-`session_id` marker.
`post-plan-hindsight-check.py` (`preToolUse`, matcher
`Write|StrReplace|Shell|EditNotebook`) consumes and immediately deletes the
marker, runs `_hindsight_check_worker.py` under a **45s** subprocess
watchdog, and denies with `user_message` only on `resolve()` returning
`auto_resolved`/`queued`. Every outcome (clean/denied/timeout/error/crash)
is logged to `~/.hindsight/logs/post-plan-hindsight-check.jsonl` for direct
false-positive-rate observability going forward, rather than inferring it
later from `reflect()` trends alone. 40 unit tests across
`tests/test_write_plan_marker.py`, `tests/test_hindsight_check_worker.py`,
and `tests/test_post_plan_hindsight_check.py` cover every fail-open branch,
the one-shot marker-consumption guarantee (including "worker crashes but
marker is still gone"), and that `agent_message` is never emitted (only
`user_message`) on a deny.

**Post-implementation smoke test found one more real bug the unit tests
couldn't catch: system `python3` lacks `litellm`/`vertexai`.** End-to-end
testing with real stdin/JSON (not mocks) against a live plan file initially
timed out — tracing it down showed the worker was being invoked with the
system `python3`, not `~/.hindsight/venv/bin/python3`, so
`check_contradiction()` failed immediately with
`No module named 'vertexai'` before ever reaching a real network call.
Fixed at the deployment layer: `hooks/install.sh` (the reusable installer,
see below) hardcodes the enforcer's `.cursor/hooks.json` command to
`~/.hindsight/venv/bin/python3`, never a bare `python3`. Re-testing with the
correct interpreter surfaced a second, more important finding: a genuine
successful `recall()` + `check_contradiction()` round trip through the
venv Python takes **13-17s** wall-clock in practice (interpreter startup +
one HTTP hop + one Vertex AI call) — well above the original 15s watchdog
budget picked from `resolve()`'s in-process latency numbers alone, meaning
roughly half of all real checks would have silently timed out and
fail-opened before ever completing. Raised `WATCHDOG_BUDGET_S` 15→45 based
on this measurement rather than the earlier estimate.

**Deployment**: `hooks/install.sh <target-repo>` — idempotent, JSON-merges
into any existing `.cursor/hooks.json` (`hooks/_merge_hooks_json.py`, 8
tests covering preservation of unrelated existing hooks and idempotency),
symlinks the four hook scripts into `~/.hindsight/hooks/` (same
single-source-of-truth rationale as `chunking.py`'s symlink into
`~/.hindsight/`, adapted for `hooks.json`'s absolute-path-reference model
rather than `chunking.py`'s Python-import model — the two aren't the same
mechanism, since hook scripts run from each target repo's own working
directory, not from a shared process). Installed into `kubernaut`,
`kubernaut-operator`, `kubernaut-console`, and all 13 `dcm-project/*`
repos. `.cursor/hooks.json` is gitignored the same way `.cursor/mcp.json`
already is (blanket `.cursor/*`, see the 2026-08-03 entry below) — it embeds
this machine's absolute paths and won't survive a fresh clone/worktree
without re-running the installer there.

**Known limitations, restated for anyone picking this up later**: (1) relies
on `user_message`'s undocumented-but-verified behavior — a future Cursor
release could silently change this without a deprecation notice, since it
isn't the documented mechanism; (2) the `Task`-subagent `session_id` gap
above; (3) `resolve()` detects semantic conflict, not author intent, so an
occasional deny on a deliberate, correct convention change is expected
behavior, not a bug — the one-shot retry path exists specifically to make
that cheap; (4) the false-positive rate (8.3% on a 12-plan sample) is a
preflight estimate, not a production baseline — the per-check JSONL log is
the mechanism for getting a real one after a week of live traffic; (5) this
pass covers `kubernaut`/`dcm` only, matching where the recurring-correction
problem was actually observed — `engram`'s own plan-kickoffs are
deliberately not gated yet.

**Also captured, not yet built** (see this repo's todo list, not filed as
GitHub issues — see the 2026-08-03 entry below for why this repo treats
`docs/findings/` as the retrospective record and issues as the
forward-looking backlog): wiring kubernaut's existing
`check-tdd-compliance.sh`/`check-business-integration.sh` into an
`afterFileEdit` hook; a `postToolUse` hook on `TodoWrite` flagging
RED/GREEN/REFACTOR phase-collapsing; a time-windowed `reflect()` call in
`nightly-learn.py` (today's only has an all-time window, which can't show
recurrence trends); and scoping what a deterministic structural check would
even mean for `dcm-project/*` repos, which have no equivalent scripts to
reuse today.

## 2026-08-04: Purged 177 Legacy Pre-`memory_id` Pending Contradictions — Unactionable Backlog, Not Data Loss

**Context**: the previous day's 24h status report flagged that kubernaut's
pending-contradictions count had grown 174→376 since the 2026-07-31 dedup fix
and confirmed the growth was genuine (zero duplicate `(new_statement,
memory_id)` pairs — see the entry below). That report also surfaced that 174
of those entries (177 once counted across all projects, not just kubernaut)
had `memory_id: null`. User asked to remove them.

**Why these were unactionable rather than just old**: `review-contradictions.py`'s
approve path needs `memory_id` (or `document_id`) to invalidate/supersede the
conflicting memory — its own code comments this exact case: *"No memory_id or
document_id on this entry (queued before the supersede fix) — old memory left
in place."* These 177 entries all predate the 2026-07-19 fix that started
threading `memory_id` through `pending_queue.append_pending()`, so a human
reviewer approving one of these would silently leave the old, contradicted
memory untouched — the review UI would look like it worked but wouldn't
actually resolve anything. Confirmed via a direct queue scan: all 177 are
timestamped between 2026-07-27 19:51 and 2026-07-31 12:54 UTC (the exact
window before that day's watermark/dedup fixes landed), spanning three
projects — kubernaut (173), dcm (3), engram (1).

**Fix**: backed up the live queue to
`contradictions-pending.jsonl.bak-legacy-purge-20260804-090826`, then filtered
out every entry with `memory_id is None` (390 → 213 entries: kubernaut
376→203, dcm 3→0, engram 1→0, koku's 10 untouched — koku onboarded well after
the memory_id fix, so none of its entries were affected). Regenerated
`docs/DASHBOARD.md` and `docs/PENDING_CONTRADICTIONS.md` via
`generate-dashboard.py` from the cleaned queue.

**Not done (and not needed)**: no fix to `pending_queue.py` itself — this was
a one-time historical cleanup of pre-fix data, not a recurring bug. Any entry
queued today already carries `memory_id` (confirmed live 2026-07-31, see
below), so this backlog of unactionable nulls cannot recur under current
code.

## 2026-08-03 (same day, third follow-up): `kubernaut-operator` Had No `.cursor/mcp.json` — Restored It, Then Verified It Survives Branch Switches

**Context**: the kubernaut-operator team reported no MCPs available in Cursor
and it was confirmed live. Global `~/.cursor/mcp.json` only carries the
shared `hindsight`/`gopls` servers by design (per
`docs/NEW_PROJECT_SETUP.md` step 8); project-specific servers
(`hindsight-docs`, `hindsight-issues`, `cocoindex-code`, `gopls`
project-scoped) come from each repo's own workspace-level
`.cursor/mcp.json`. `kubernaut-operator` simply had no such file — its
sibling repos (`kubernaut`, `kubernaut-v1.5`, `kubernaut-v1.6`,
`kubernaut-console`) all had one. Fixed by creating
`kubernaut-operator/.cursor/mcp.json` mirroring `kubernaut-v1.5`'s config.

**Follow-up question — will this survive branch switches in that repo?**
Checked `.gitignore`: `kubernaut-operator` blanket-ignores `.cursor/*` (with
`!.cursor/rules/`/`!.cursor/skills/` carved back out, no exception for
`mcp.json`) — same convention as `kubernaut`/`kubernaut-v1.5`/
`kubernaut-v1.6`. Verified empirically rather than just asserting it: `git

## 2026-08-03 (same day, follow-up): Every `*-cocoindex-flows.py` Was Holding a Default-Sized 10-Connection Postgres Pool It Never Needed

**Context**: user noticed "a lot of postgres running instances" after the
engram service restart above and asked whether they were actually needed.
`ps aux | grep postgres` showed only **one** real `postgres` server process
(plus its normal fixed set of background workers: checkpointer, walwriter,
autovacuum launcher, logical replication launcher, 3 io workers, logger) —
so "instances" in the visual sense was a red herring; the real question was
the ~18 separate `postgres: hindsight hindsight 127.0.0.1(port) idle` client
backend rows underneath it. Cross-checked against `pg_stat_activity` directly
(`max_connections=100`, 28 total connections counted, 20 against the
`hindsight` database) rather than guessing from `ps` output alone.

**Root cause**: every `*-cocoindex-flows.py` calls `postgres.create_pool(PG_DSN)`
with **no `min_size`/`max_size` kwargs** for its `code_app`'s pgvector
`PG_POOL` — confirmed `cocoindex.connectors.postgres.create_pool()` is a thin
pass-through to `asyncpg.create_pool()`, whose own library defaults are
`min_size=10, max_size=10`. Since `min_size == max_size` by default, each
pool isn't elastic at all — it eagerly holds exactly 10 connections open for
the lifetime of the process, regardless of how often `code_app` actually
touches Postgres (in practice: rare, bursty pgvector upserts triggered only
by real file changes, not sustained concurrent traffic). Two processes were
running live at the time (`io.vectorize.cocoindex.service` for kubernaut,
`io.vectorize.cocoindex.engram`), so that's up to 20 connections held open
just for two lightly-used pools — and this multiplies by one more full
10-connection pool for every additional project onboarded (`koku`, `dcm`)
once their flows run in live mode, none of which was ever deliberately
decided, just inherited from never overriding the constructor's defaults.

**Fix — right-sized, not eliminated**, following the exact same philosophy
already applied to `hindsight-api`'s own pool on 2026-08-02 (re-derive a
number from actual observed usage rather than accepting or blindly
multiplying a vendor default): added `PG_POOL_MIN_SIZE`/`PG_POOL_MAX_SIZE`
module constants (env-overridable via `COCOINDEX_PG_POOL_MIN_SIZE`/
`COCOINDEX_PG_POOL_MAX_SIZE`, defaulting to **2/5**) to all four
`*-cocoindex-flows.py` files, passed into their `create_pool()` calls.
2 keeps a small warm floor (avoids reconnect latency on the next write); 5
still allows real parallelism during an initial full-repo backfill walk,
just not 2x more than that walk realistically drives concurrently. Made the
new env vars explicit in the `service`/`engram`/`koku` launchd plists
alongside their existing (already-explicit-despite-matching-the-code-default)
`COCOINDEX_PG_URL` entry, for the same discoverability reason — `dcm.plist`
was left alone since it doesn't set `COCOINDEX_PG_URL` either (it runs
`dcm-cocoindex-flows.py` as a one-shot nightly `StartCalendarInterval` batch
job via `dcm-nightly-ingest.sh`, not a `KeepAlive` live daemon, so it was
never actually contributing to the steady-state connection count in the
first place — confirmed by cross-checking its plist rather than assuming).

**Verified before/after**: full test suite still 351/352 passing (same
pre-existing, unrelated `check-rule-sync` failure as the entry above) after
the change. Restarted both currently-live services
(`io.vectorize.cocoindex.service`, `io.vectorize.cocoindex.engram`) to pick
up the new pool sizing immediately rather than waiting for their next
natural restart.

**Reconciled every connection after restart, not just the rough count.**
Post-restart, `pg_stat_activity` still showed ~20 total connections to
`hindsight` — barely changed from before, which could have looked like the
fix did nothing. Split by `backend_start` relative to the restart instant:
exactly **4** connections dated from the restart itself (two near-identical
timestamps 12:44:04.554/.555 and 12:44:04.575/.576 — `min_size=2` firing for
each of the two pools, precisely as configured, down from 10+10=20 before),
and the other **15** all predated the restart and were untouched by it —
tracked to PID 28480 (`hindsight-api`, blue, running since 1:00 AM, 66% CPU
at the time), sitting exactly at its own already-deliberately-tuned

running near-saturated with legitimate background work at the exact moment
of the before/after comparison, not a sign the fix underperformed.

## 2026-08-03: The "Still-Open" `kubernaut-issues` Redundancy Root Cause — Positional Chunk IDs Cascading on Every Prepend/Comment, Not `hindsight-api`'s Delta-Diff

**Context**: direct follow-up to the branch-switching-churn entry below, which
explicitly flagged `kubernaut-issues`' redundancy as a **different, still-open**
root cause (line ~130 of this file, same day) and floated two possible fixes:
registering a real `"exact"` strategy in `hindsight-api`, or fixing its
delta-diff. Investigated `hindsight-api` (a third-party PyPI package, not
this repo's source) to act on the first option and found `strategy: "exact"`
was never registered *client-side* either — every `hindsight_retain()` call
across all four `*-cocoindex-flows.py` files sent a `"strategy": "exact"`
field that `hindsight-api` silently ignores (confirmed against its OpenAPI
spec: no such field exists on the retain-items schema). It was dead code,
not a broken feature — there was nothing to "register."

**Real root cause — cascading positional chunk IDs, not `hindsight-api` at
all.** `_split_text()` in every flow file chunked docs/issues by fixed
character offset and derived `document_id`s from the chunk's *index*
(`{base_id}--chunk{i}`). Any edit before a given offset — prepending a new
`## Section` to a markdown file, or a new comment landing on an issue/PR —
shifts every downstream chunk's boundaries, so chunk `i`'s *content* is now
different from what chunk `i` was last time, even though the actual prose
in that chunk never changed. `hindsight-api` correctly sees "different
content at this `document_id`" and does a full re-extraction — this was
never a delta-diff bug, it was engram feeding it a legitimately-different
payload every time. `docs/FINDINGS.md` itself (edited almost exclusively by
prepending new dated entries at the top, exactly like this edit) and any
issue/PR that accumulates comments over time are worst-case inputs for this
pattern — which lines up with `kubernaut-issues`' measured ~4x redundancy
(60,762 units / 15,226 distinct `document_id`s, previous entry) far better
than a `hindsight-api` delta-diff bug would.

**Fix — content-anchored chunk IDs, not positional ones, plus dropping the
dead field.** New shared module `chunking.py`, imported by all four
`*-cocoindex-flows.py` (symlinked into `~/.hindsight/chunking.py`, see
`docs/INSTALL.md` step 16):

- `split_fixed_window()` — the original offset-based splitter verbatim,
  kept as the fallback for oversized sections that have no better anchor.
- `split_markdown_sections()` — splits on `^#{1,6} ` heading boundaries
  instead of raw offsets, keyed by a short sha1 digest of the heading line
  itself (stable across prepend/reorder), falling back to
  `split_fixed_window()`-style numbering only for oversized content within
  one section.
- `split_issue_sections()` — one section for the static header+description,
  then one section per comment keyed by the comment's **ordinal position in
  the already-filtered comment list** (`comment{i}`), not by character
  offset into a concatenated string — so a new comment #6 never touches
  comments #1-5's `document_id`s or content.
- Every flow's issue/PR/Jira-issue formatter was also split into a static
  header (title/author/created/description) and per-comment sections, with
  volatile fields (`state`, `labels`) deliberately **excluded** from the
  chunked header — they're already carried in `metadata`/`tags`, which
  `hindsight-api` can update without a content-hash change. Previously
  every state transition (e.g. `OPEN`→`CLOSED`) or label edit silently
  rewrote the *entire* issue body's content, forcing full re-extraction of
  unrelated description text along with it.
- Removed the dead `strategy: "exact"` field entirely rather than replacing
  it with `hindsight-api`'s real `retain_extraction_mode: "verbatim"`/
  `"chunks"` options — both were evaluated and rejected: `"verbatim"` still
  calls an LLM (just for metadata, not synthesis) so it wouldn't have
  addressed the redundant-Sonnet-consolidation cost either; `"chunks"`
  skips LLM extraction entirely but trades away fact-synthesis recall
  quality repo-wide, a bigger tradeoff than this fix required.

**Test coverage** — `tests/test_chunking.py` (new) plus regression tests
added to each flow's existing test file (`test_cocoindex_flows.py`,
`test_engram_cocoindex_flows.py`, `test_koku_cocoindex_flows.py`, and new
`test_dcm_cocoindex_flows.py`) asserting: prepending a section leaves
earlier sections' `document_id`/content untouched, appending a comment
leaves earlier comments' `document_id`/content untouched, a state/label
change leaves the header's `document_id`/content untouched, and the
`strategy` field is absent from the retain payload. Full suite run:
352 tests, 351 passed — the 1 failure (`test_check_rule_sync.py`'s
four-pairs assertion, pre-existing since the koku-onboarding commit
earlier the same day) is unrelated and reproduces identically on a clean
`git stash`.

**Fixed `dcm-cocoindex-flows.py`'s `PG_POOL` `ContextKey` collision as a
side effect of getting it under test** — it shared the literal string
`"pg_pool"` with `cocoindex-flows.py`'s own `ContextKey`, which only
explodes with `ValueError` once both modules load into the *same* process
(e.g. pytest collecting both test files together) — renamed to the
per-file-unique `"dcm_repo_pg_pool"`, matching the pattern
`engram-cocoindex-flows.py`/`koku-cocoindex-flows.py` already used.

**Timing**: deployed before the previous entry's 3:00 AM
`cleanup-kubernaut-docs-issues.sh` one-shot ran, specifically so
`kubernaut-docs`/`kubernaut-issues`' from-scratch backfill would build its
initial `document_id` set using the new stable scheme rather than the old
positional one — avoiding a second full re-backfill later just to pick up
this fix.

## 2026-08-03: Runaway CocoIndex Re-ingestion From Branch-Switching Churn — Live Dev Clones Replaced With Branch-Scoped Mirrors

**Context**: woke up to `kubernaut-docs` unconsolidated memory units spiking
7,594 → 43,972 in 15 minutes, `kubernaut-issues` showing the same continuous
churn, and `hindsight-stdout-blue.log` full of `Extract facts:` / `no
unchanged chunks... falling back to full retain` lines — each one paying a
real Vertex AI Sonnet consolidation call. Immediately stopped all three
kubernaut-family/dcm/engram CocoIndex `launchd` jobs (`io.vectorize.
cocoindex.service`, `.engram`, `.dcm`) via `launchctl bootout` to cut off new
spend while root-causing.

**Where Sonnet actually sits in the pipeline** (came up mid-investigation,
worth recording since it shaped the fix): `cocoindex-flows.py`'s own
`process_doc_file`/`process_issue` never call an LLM directly — they do plain
character-based chunking (`_split_text`) and push raw text to
`hindsight_retain()` over HTTP. Every `slow llm call` line in
`hindsight-stdout-blue.log` is tagged `scope=consolidation,
model=litellm/vertex_ai/claude-sonnet-4-6` — Sonnet is invoked **server-side,
inside `hindsight-api`**, exclusively for the background consolidation worker
that merges/dedupes/synthesizes raw retained chunks into curated
observations and mental models. Retain-time fact extraction is a separate,
much faster call (~3.4s for one chunk vs. 15-70s for a consolidation batch),
consistent with a lighter model. So the cost is structural: anything that
causes redundant re-`retain()`s of unchanged content pays for redundant
Sonnet consolidation on top, even though CocoIndex itself never touches an
LLM for docs/issues.

**Root cause — traced via exact file-count matching, not inference.** Found
`docs/architecture/decisions/DD-AUDIT-003-...md` had an mtime of 06:15 AM
today despite `git status` being clean and the last real commit dated
2026-08-02 20:16 — the file's *content* hadn't changed, only its mtime.
`find docs -name "*.md" -newermt "06:00" ! -newermt "06:30" | wc -l` returned
**135** — the exact same count as the "falling back to full retain" events
logged in that window. `git reflog` for the live kubernaut clone showed why:

```
06:15:41 checkout: moving from fix/1861-vertex-ai-explicit-credentials to main
06:15:42 pull origin main --quiet: Fast-forward
06:18:44 checkout: moving from main to fix/1869-sre-persona-approval-visibility-rbac
06:20:19 commit: fix(apifrontend): ... (#1869)
```

Routine automated branch-switching (PR work) touches the mtime of every file
that differs between whichever two branches were involved in each checkout —
`cocoindex-flows.py`'s `docs_app`/`code_app` used
`localfs.walk_dir(..., live=True)` pointed directly at the **live, actively
branch-switched dev clones** (`~/go/src/github.com/jordigilh/kubernaut`,
`-operator`, `-console`, `-demo-scenarios`, `-docs`). CocoIndex correctly
detected the touched mtimes as "changed" and reprocessed them, but the delta
was branch-switching noise, not real content evolution — a `strategy:
"exact"` no-op-if-unchanged flag in `hindsight_retain()` calls was also
silently never registered in `hindsight-api`'s config, so every one of these
resubmissions fell all the way through to a full delta-diff and, per the
`no unchanged chunks` log line, `hindsight-api`'s own diff also failed to
recognize the resubmitted content as identical.

**Fix — stop watching the live checkout entirely, watch dedicated
branch-scoped mirrors instead.** Checked `cocoindex/connectors/` first: no
native git-ref source exists, only `localfs`/`postgres`/`surrealdb`. So the
fix is at the git level, not CocoIndex's:

- `watch-mirrors-config.sh` — single source of truth, a `name|live_clone|
  branch|mirror_path` array. 6 entries: `kubernaut`, `kubernaut-operator`,
  `kubernaut-console`, `kubernaut-demo-scenarios`, `kubernaut-docs` (all
  `main` — `release/v1.5` was considered and explicitly dropped: it's
  diverged enough that `main` is now authoritative, and other repos' release
  branches are already covered via issue tracking), plus `engram` itself.
- `watch-mirrors-lib.sh` — `ensure_mirror()`: `git fetch origin <branch>`,
  then either `git worktree add --detach <mirror_path> origin/<branch>`
  (first run) or `git -C <mirror_path> reset --hard origin/<branch>`
  (subsequent runs). Sourced by both `setup-watch-mirrors.sh` (one-time
  bootstrap) and `refresh-watch-mirrors.sh` (periodic sync, new
  `io.vectorize.cocoindex.watch-sync.plist`, every 600s) so they can't drift
  apart.
- **Why `reset --hard` on a single branch actually fixes the "unknown
  delta" problem, not just relocates it**: `git checkout` between two
  *divergent* branches touches the mtime of every file that differs between
  them — which can be huge and has nothing to do with real content
  evolution. `git reset --hard` moving *forward along one branch's linear
  history* only rewrites the mtime of files whose blob actually changed in
  the new commits. Watching mirrors that only ever fast-forward `main` turns
  "file changed" back into a real, trustworthy content signal, by
  construction — no CocoIndex-side patching needed.
- `ENGRAM_DOCS_DIR`/`ENGRAM_CODE_DIR`/`ENGRAM_OPERATOR_DIR`/
  `ENGRAM_CONSOLE_DIR`/`ENGRAM_SCENARIOS_DIR` (in `io.vectorize.cocoindex.
  service.plist`) and `ENGRAM_REPO_DIR` (in `io.vectorize.cocoindex.
  engram.plist`) now point at `~/.hindsight/watch/<repo>` instead of the
  live clones — and the same paths were made the *default* fallback in
  `cocoindex-flows.py`/`engram-cocoindex-flows.py` (previously only the
  plists overrode the unsafe live-clone defaults; a manual `python3
  cocoindex-flows.py` invocation would have silently used them).
- `code_app` was brought into the same fix, not just `docs_app`, despite
  costing no LLM calls: `code_embeddings` turned out to have zero true
  duplicate `(filepath, chunk_index)` rows (real primary key, clean
  upserts — the largest per-file chunk counts, e.g. 1,919 for
  `oas_json_gen.go`, are legitimate: that generated file is 1.29MB/50,534
  lines, verified against the live checkout), so the risk there was never
  storage bloat — it was `engram_code_search` relevance silently drifting
  toward whichever feature branch happened to be checked out at the last
  reprocessing, not "current main."
- **`engram` itself was triaged, not just assumed safe** because it's
  smaller: `engram-cocoindex-flows.py` has the structurally identical
  `walk_dir(ENGRAM_REPO_DIR, live=True)` pattern. It shows zero symptom
  today only because its `git reflog` has zero branch checkouts (`commit:`/
  `reset:`/`commit (amend)` only — engram is worked on via direct commits to
  `main`) and zero `falling back to full retain` occurrences in its logs.
  That safety is behavioral, not architectural, and will evaporate the
  moment engram's own workflow adopts feature branches — so it was added to
  `watch-mirrors-config.sh` now, as a zero-cost future-proof, rather than
  deferred.
- **Verified the actual fix, not just the restart**: after redeploying,
  checked out `main` and back to the original feature branch in the *live*
  kubernaut clone (the exact churn pattern that caused this morning's
  incident) and confirmed zero new `docs_app`/`code_app` activity in
  `cocoindex-stderr.log` — only the unrelated scheduled issues-poll. The
  mirror at `~/.hindsight/watch/kubernaut` never moved.

**Database size, measured directly (not guessed) — confirms months of this
churn already landed in the corpus.** Hindsight's own tables total **~9.2GB**:
`memory_links` 6534MB (dominant — relationship/co-occurrence edges scale with
every duplicate memory unit, compounding faster than linear), `memory_units`
2032MB, `llm_requests` 220MB, `unit_entities` 142MB, `documents` 131MB,
`chunks` 119MB, `entity_cooccurrences` 72MB. `kubernaut-docs`: 142,178 memory
units for only 40,406 distinct `document_id`s (~3.5x redundancy).
`kubernaut-issues`: 60,762 units for 15,226 distinct `document_id`s (~4x).
Note `kubernaut-issues`' redundancy has a **different, still-open** root
cause than docs: `issues_app` polls the GitHub API every 300s, never touches
local filesystem state, so it was never subject to the branch-churn bug
above — its `process_issue` is already `@coco.fn(memo=True)`, so the
redundancy most likely comes from `hindsight-api`'s same broken
"no-unchanged-chunks → full retain" fallback firing on *genuinely* updated
issues/PRs (new comments, label/state changes) over the weeks this pipeline
has run, not from CocoIndex resubmitting identical content. The mirror fix
does not address this — flagged as a follow-up (registering a real `"exact"`
strategy in `hindsight-api`, or fixing its delta-diff, would).

**Cleanup scheduled off-hours, not run immediately.** Clearing
`kubernaut-docs`/`kubernaut-issues` (`DELETE /v1/default/banks/{bank_id}/
memories` — confirmed via `hindsight-api`'s own OpenAPI spec, backs
`clear_memories`) does *not* by itself cause CocoIndex to resubmit anything:
`@coco.fn(memo=True)` memoization in `cocoindex.db` tracks "already
processed" independently of `hindsight-api`'s state, so a cleared bank stays
empty until `cocoindex.db` is also reset. That's safe for `code_app`
(idempotent `pgvector` upserts) and `transcript_app` (protected by its own
separate watermark file, see 2026-07-31 entry — unaffected by resetting
`cocoindex.db`), but for `docs`/`issues` a real reset means re-extracting
~55K documents from scratch, which empties both banks for the duration
(potentially hours) — and both are on kubernaut's *mandatory* recall list.
Rather than run this mid-morning, wrote `cleanup-kubernaut-docs-issues.sh`
(stop the service, clear both banks, back up and reset `cocoindex.db`, run
`cocoindex-flows.py --mode backfill --apps docs issues`, restart the
service) and scheduled it via a new one-shot `io.vectorize.cocoindex.
cleanup-once.plist` (`StartCalendarInterval` 3:00 AM) that self-removes
(`launchctl bootout` + `rm` its own plist) after running once, so it never
fires a second night.

## 2026-08-02: Zero-Downtime Blue/Green Restart for `hindsight-api` — And a Real Connection-Leak Bug Found Along the Way

**Context**: direct follow-up to 2026-07-07's "Cursor shows the MCP as down
every morning" (not fully solved) and the intervening work to move the
nightly restart from a stale-cached 3pm/2pm trigger to a clean 1am
(`UserEventAgent` was holding a stale calendar-trigger cache; killing and
letting it respawn fixed the schedule itself — separate from this entry).
Fixing *when* the restart happens didn't fix the actual complaint: whenever
it fires, Cursor's HTTP MCP client to `hindsight`/`hindsight-docs`/
`hindsight-issues` (all served by the same `hindsight-api` process on
`:8888`) drops and never auto-retries, staying disabled until a manual
reload — regardless of the hour. Before building anything, checked whether
the restart was even still *necessary* at the current heap level: 11h into
that day's uptime, RSS was 410MB (vs. the 17GB crisis and even the 1GB
post-fix baseline from 2026-06-26) — strong evidence the GPU/pool-size fixes
from that entry already did the heavy lifting and the *blind daily* restart
is overkill most days. User's call: keep the schedule as-is, but make the
restart's *impact* zero instead of reducing its frequency.

**Fix, part 1 — architecture**: `hindsight-api` no longer binds `:8888`
directly. It now runs as a **blue/green pair** (`io.vectorize.hindsight.
service-{blue,green}.plist`, internal ports 18888/18889, exactly one loaded
at a time) behind `hindsight-proxy.py` — a ~90-line stdlib-only asyncio TCP
proxy that is the *only* thing that ever binds `:8888` and is never touched
by the restart job. `hindsight-blue-green-restart.sh` (invoked by
`io.vectorize.hindsight.restart.plist` in place of the old `pkill -f
hindsight-api`) does a real make-before-break swap: start a fresh instance
on the standby color, wait for it to pass a readiness gate, flip the proxy's
active-backend state file (`~/.hindsight/state/active-backend.port`, re-read
per new TCP connection), drain the old instance for 10s, tear it down. Port
8888 never refuses a connection at any point.

**Fix, part 2 — the readiness gate had to be stricter than "`/health` says
200"**: first live test looked broken — port 8888 (and the backend
*directly*, bypassing the proxy entirely) went fully unresponsive for
60-70s, well after the swap script had already declared victory and moved
on. Root cause was **not** the proxy: `hindsight-api` passes `/health`
almost immediately on startup, then its in-process worker claims a startup
burst of recovered/pending tasks up to `HINDSIGHT_API_WORKER_MAX_SLOTS`
(default 10) — and because no `HINDSIGHT_API_READ_DATABASE_URL` is
configured (single embedded Postgres, no read replica), there is only **one**
shared DB connection pool for everything: worker tasks *and* HTTP-serving
recall/health requests. A worker claiming its full default of 10 tasks
against a pool sized 10 (the 2026-06-26 fix) can claim every connection,
starving incoming HTTP requests until a task completes. `/health` itself
is cheap enough to occasionally slip through fast, which is why a single
200 wasn't a reliable readiness signal. **Fix**: the swap script now
requires 5 *consecutive* checks that both succeed and complete within 2s
before declaring the standby ready (`HEALTH_TIMEOUT_S` raised 90→180s to
give this room) — a slow/queued check resets the counter to zero.

**Fix, part 3 — tuned the actual contention source**: bumped
`HINDSIGHT_API_DB_POOL_MAX_SIZE` 10→15 and added
`HINDSIGHT_API_WORKER_MAX_SLOTS=5` (previously unset, defaulting to 10) to
`config.env`/`config.env.example`. 15 was picked deliberately over reverting
to upstream's default of 100 — that default was directly responsible for
6.6GB of the original 17GB heap leak (2026-06-26), and this repo already
has a documented instance of "restore the old default" being the wrong
instinct for this exact setting. 5 worker slots leaves ≥10 of 15 connections
free for HTTP even at the worker's own claimed maximum. Confirmed via the
worker's own `[WORKER_STATS]` log line before/after: `slots=10/10 ...
pool: size=10 ... pending_acquires=37` (saturated) →
`slots=5/5 ... pool: size=15 ... pending_acquires=0` (headroom) on a fresh
restart under equivalent load.

**Bug found along the way (candidate for upstream report, alongside the
still-open #2529/#2534 from 2026-07-02/07-07)**: a Postgres backend was
found `idle in transaction` for **19+ minutes**, permanently pinning one
pool slot until the owning `hindsight-api` process was killed. Traced to a
`graph_maintenance` task that failed with an `asyncpg` `TimeoutError`
(`claim_graph_maintenance_batch` → `conn.fetch` → `bind_execute`) — the
failure path did not roll back or release the connection. Each occurrence
permanently shrinks the *effective* pool size until the process restarts,
compounding any contention rather than just being a one-off slow query. Not
yet filed upstream; worth reproducing in isolation and reporting if it
recurs outside of artificially heavy load (see next finding for how it was
triggered here).

**Methodology lesson — the first "outage" during testing was self-inflicted,
and it briefly looked exactly like a production bug.** Verifying the swap
with a tight-loop curl monitor (sub-second spacing, dozens of requests in
under two minutes, one run's monitor still finishing while the next test
already started) drove `pending_acquires` far higher than any plausible
real Cursor traffic pattern would, and combined with the connection-leak bug
above to produce a genuine multi-minute full outage — which was easy to
mis-read as "the proxy is broken" before checking `pg_stat_activity`
directly. Switching to *gently paced* verification (single requests, 2-3s
apart, one test run allowed to fully settle before starting the next) both
reproduced the real, worth-fixing readiness-gate gap **and** cleanly
confirmed zero downtime once the fixes above were in place — 135s of
3s-spaced health checks spanning an entire live swap, zero failures.

**Docs updated**: `docs/README.md` (architecture diagram + components
table), `docs/INSTALL.md` (install steps 5/troubleshooting/upgrading/
uninstall), `docs/COCOINDEX.md` (restart command in its pg0 troubleshooting
section) — all previous single-`io.vectorize.hindsight.service.plist`
references replaced with the blue/green + proxy equivalents.

**Takeaways**:
- **A liveness/health check answering fast on its own is not the same
  question as "can this instance absorb real traffic right now."** A
  process can be honestly healthy (DB reachable, app initialized) and still
  be functionally saturated moments later by its *own* background work
  competing for the same finite resource (here: one DB connection pool
  shared between a startup task-claim burst and user-facing requests, with
  no read/write pool separation configured). Readiness gates for any
  make-before-break swap need to probe for sustained responsiveness, not a
  single passing check.
- **When a fix moved a setting away from a vendor default for a documented
  reason (here: pool size, to fix a heap leak), don't casually 10x it back
  toward that default to solve a new, different problem.** Re-derive a
  number from the *current* evidence (the worker's own claimed-task ceiling)
  instead — got the contention relief without reintroducing the leak.
- **Synthetic load-testing a shared, stateful backend without deliberate
  recovery time between runs can manufacture an outage that looks identical
  to a real one.** Always check the datastore's own session/lock view
  (`pg_stat_activity` here) before concluding a symptom is in the layer
  you're actively testing (the proxy) rather than a downstream one.
- **A repeated, silently-inconsistent test harness (interrupting a
  multi-step script mid-flight) can leave *its own* infrastructure in a
  half-migrated state** — an interrupted swap attempt left a bootstrapped
  standby instance behind that caused an unrelated-looking `launchctl
  bootstrap` `Input/output error` on the next attempt. Worth explicitly
  reconciling to a known-clean state after any interrupted test, not just
  retrying.
